# Remaining Screen Alignment Design

## Context

The first WalnutPi screen sync slice is already implemented: Web renders the current screen manifest, sync validates `manifestHash`, delivery uses the SSH/local-agent adapter, the device returns screen state and framebuffer evidence, and the Web console can show sync history, repair candidates, and evidence-limited AI summaries.

The remaining alignment work is not one large rewrite. It splits into three safe product slices plus a real-device regression check:

1. Real-device sync regression evidence.
2. Minimal WalnutPi memory and skills context for AI answers.
3. Stronger visual consistency evidence.
4. A repair loop that can propose a patch but cannot apply it without explicit confirmation.

## Goals

- Preserve the beginner-first workflow: preview first, sync to WalnutPi, show understandable status, keep hashes and command output in diagnostics.
- Make WalnutAI answers more WalnutPi-specific by loading a small local context bundle.
- Add a first pixel-evidence contract that is diagnostic-only and does not claim full visual equality.
- Move repair from read-only advice to a confirmation-gated patch proposal flow.
- Keep all high-risk actions behind explicit confirmation and clear impact text.

## Non-Goals

- Do not turn the Web app into a general IDE or code editor.
- Do not add unauthenticated system writes, public root shells, image flashing, eMMC writes, reboots, shutdowns, or GPIO output.
- Do not auto-apply repair candidates, auto-run SSH, auto-restart services, or auto-resync from repair generation alone.
- Do not claim pixel-perfect equality between Web and LVGL unless the system actually compares both renderings.

## Slice 1: Real-Device Regression Evidence

Use the existing evidence script with `-Sync` after the user explicitly confirms device writes:

```powershell
pwsh ./scripts/collect-screen-sync-evidence.ps1 -Sync -Port 4183
```

The result should be recorded in `docs/third-projects-integration-alignment.md` with concrete `buildId`, hashes, `visualMatch`, frame SHA, service state, and ownership notes.

## Slice 2: Minimal WalnutPi Memory And Skills

Create a small repo-owned context bundle under `walnut-ai-terminal/skills/`:

- `walnutpi-core.md`: board and product facts, current project direction, safety boundaries.
- `walnutpi-screen.md`: `/dev/fb0`, 480x320, RGB565, LVGL fbdev, `walnut screen` command boundaries, Web sync evidence.

Add a non-secret memory seed:

- `walnut-ai-terminal/memory/default-memory.json`

Update `walnut-ai-terminal/walnut_ai.py` so it loads:

- `WALNUT_AI_CONTEXT_DIR`, defaulting to `walnut-ai-terminal/skills`
- `WALNUT_AI_MEMORY_FILE`, defaulting to `walnut-ai-terminal/memory/default-memory.json`

The loaded context is appended to the system prompt. Missing files are ignored. The loader must not read secrets, logs, API keys, SSH passwords, Wi-Fi passwords, or arbitrary directories.

## Slice 3: Pixel Evidence Contract V1

The current `screenEvidence.visualChecks` already records structural framebuffer checks and semantic signature hashes. Add a narrow `pixelEvidence` object under `screenEvidence`:

```json
{
  "schema": "walnutpi.screenPixelEvidence.v1",
  "status": "metadata-only",
  "claim": "framebuffer-captured-not-pixel-diffed",
  "frameHash": "...",
  "sampleHash": "...",
  "nonzeroRatio": 0.123,
  "capture": {
    "width": 480,
    "height": 320,
    "pixelFormat": "RGB565_LE",
    "byteLength": 307200
  },
  "limitations": [
    "Web preview pixels are not rendered and compared in this slice.",
    "LVGL may be dynamic, so diagnostic PNG can be later than sync-time raw frame."
  ]
}
```

This does not change `visualMatch`. It gives future pixel diff work a stable home without overstating current guarantees.

## Slice 4: Confirmation-Gated Repair Patch Proposal

Add a new read-mostly route:

```text
POST /api/screen/repair-proposal
```

Input:

```json
{ "buildId": "screen-..." }
```

Output:

```json
{
  "schema": "walnutpi.screenRepairProposal.v1",
  "buildId": "screen-...",
  "canApply": false,
  "requiresConfirmation": true,
  "confirmationPhrase": "APPLY SCREEN REPAIR <buildId>",
  "proposedPatch": null,
  "notes": []
}
```

For this slice, the route may only propose safe local manifest repairs for manifest-stage failures when the persisted record has enough evidence to construct a replacement `lvgl_app/screen-manifest.json`. It must not run build, SSH, activation, capture, or sync.

Add a second route for explicit application:

```text
POST /api/screen/repair-apply
```

Input:

```json
{ "buildId": "screen-...", "confirmation": "APPLY SCREEN REPAIR screen-..." }
```

The apply route must:

- Reject `?nossh` only if the planned action would touch the device. Local manifest writes can run in normal mode but must still require confirmation.
- Validate `buildId` and confirmation phrase.
- Apply only the exact proposal generated by the server.
- Write local files only inside the repo.
- Not sync automatically after applying.
- Return a summary telling the user to preview and manually sync after reviewing.

If no safe local patch exists, the proposal returns `canApply=false` and describes manual next steps.

## Verification

- Real-device sync script succeeds and prints build/evidence fields.
- `git diff --check` passes for touched files.
- AI context loader can run without `OPENAI_API_KEY`.
- `POST /api/screen/ai-summary?nossh` still works for a stored record.
- Pixel evidence appears in a sync result and record after a real or synthetic successful sync.
- `POST /api/screen/repair-proposal?nossh` returns a proposal for a temporary failed record without device actions.
- `POST /api/screen/repair-apply?nossh` rejects missing or wrong confirmation.
